# UX / Ergonomics Review — 2026-10-14

Review at `9e96c03`, by persona. Done by driving the dev app in a browser
(desktop 1366 px and phone 390 px) and reading the frontend code.
The 2026-10-12 review (`code-review-2026-10-12.md`) covered individual flow
bugs (U/V items). This one looks at whether each kind of user can do their job.

Prefixes: **D** director / approvers · **I** IT team · **E** everyone
(admin staff, scientists, students).

## Summary

The building blocks are good. The "Awaiting my action" cards are clear and
colour-coded by age, and the request page has a clean Approve / Reject panel.

The main problems are about *finding things*:

1. The director's to-do list is pushed below the welcome pages, and there is
   no reminder when something sits too long.
2. IT has no single place that says "something is wrong". Failed AD steps,
   stuck mails and the AD sync are each hidden in a different screen.
3. The top bar has 11 tabs. It overflows on a laptop and is unusable on a phone.

## Status

`/change-password` (account menu, or automatically when the login finds an
expired one). IT has a "Reset password" button on AD users in People, which
also unlocks the account. Unlock-only and group editing are still open.
**Done (batch 1):** D1, D3 (closed requests now filter on their last

**Not verified against the real AD:** the Kerberos path for expired

## Director / approvers

### D1 High — the to-do list is below the fold
`dashboard.py:58-63`. The dashboard draws the published pages first ("Welcome",
"Onboarding guide"…), then "Awaiting my action". The director sees the same
three welcome cards every day, and the cards he must act on start lower.
On a phone they start after three full-screen cards.
→ Order: Awaiting my action, then My requests, then pages (or move pages to
the Pages tab only, for logged-in users).

### D2 High — no reminder for stale requests
The scheduler runs only the booking reminder and the retention purge
(`app.py:58-65`). A request can sit at "Approval" for weeks. The card turns
red, but only if the director opens the app.
→ A daily (or weekly) digest email per approver: "You have N requests
waiting, oldest is X days". The urgency thresholds already exist in
`dashboard_config`. Skip the mail when N = 0.

### D3 High — open requests disappear from "My requests" after 30 days
`workflow_service.py:697,753` filter on `created_at >= since`, and the
default period is "Last 30 days". An onboarding started 5 weeks ago and
still waiting on the newcomer is no longer listed. It looks done.
→ Always include requests that are still in progress, whatever the period.
The period should only limit closed requests.

### D4 Medium — nothing shows what I already handled or who is blocking
"All requests" (admins) / "My requests" (others) is either everything or only
what I created. A director can't see "requests I approved" or "requests
waiting on someone else". There is no "Waiting for" column: an onboarding
stuck 6 days at "Newcomer information" doesn't say the newcomer is the
blocker, so nobody knows whom to chase.
→ Add a "Waiting for" column (person, role name or "newcomer"). Add a
filter "In progress / Closed / All" defaulting to In progress.

### D5 Medium — the age badge is shown on closed requests
In the requests table, rejected and completed rows still show a red
"9d" badge. It reads as "late" when it is finished.
→ Hide the age for closed requests (or show the closing date).

### D6 Medium — approving several requests is slow
After Approve, the page reloads the same request
(`workflow_detail.py:452,459`). The director clicks Back, finds the next
card, opens it. For five VPN requests that is 15 clicks.
→ After an action, go to the next pending request (or back to the
dashboard with a toast). A "Next pending (4 left)" button is the simplest.

### D7 Low — onboarding cards show an email, not a name
Cards show `wei.zhang@cas.cn` until the newcomer fills the form, because
`_target_display` (`dashboard.py:100`) only reads `target_name` / `person_name`.
After the newcomer step, `first_name` + `last_name` exist but are not used.
→ Also read `first_name`/`last_name`.

### D8 Low — Delete sits next to the status on the request page
A red DELETE button is in the header, next to "In progress". It is the
most visible action on the page for an admin, and the least frequent.
→ Move it into a "⋮" menu.

## IT team

### I1 High — no single "is anything wrong?" view
Things IT needs to watch are scattered:

| Signal | Where it is today |
|--------|------------------|
| Failed AD steps (`workflow_failed_effect`) | only on each request's own page |
| Mails failing / pending | Settings → Email/SMTP → Outbox (inside an expansion) |
| AD sync button + result | Settings → LDAP section |
| AD config errors (e.g. empty `users_ous`) | nowhere, the AD step just fails |
| Critical audit events | Audit log, mixed with logins |

In the dev DB there are 2 failed AD effects and nothing on any list says so.
→ An "Operations" panel (first section of the IT tab, see E1) with counters
that turn red: failed AD steps (with links to the requests), failed mails,
pending mails older than 1 h, last AD sync date and result, config warnings.
Show a badge on the tab when a counter is non-zero, like the dashboard badge.

### I2 High — "Completed" in green while AD was not updated
The two requests with failed `ad_add_to_groups` show a green "Completed"
badge in the requests table. Nobody opening the dashboard can tell the
person never got their VPN group.
→ A distinct status display: "Completed — action needed" (orange), driven by
the existence of pending failed effects.

### I3 High — the audit log is all red
Every superuser login is "critical". In 30 days of dev data: 21 critical
rows, all logins. A real critical event (role change, failed logins burst)
would be lost.
→ Make a successful superuser login "sensitive", not "critical". Keep
"critical" for things someone should look at. Consider defaulting the
severity filter to "Sensitive + critical".

### I4 Medium — AD management is split over four places
- Users tab (superuser only): list, last AD logon, bulk enable/disable.
- People tab: edit one person, enable/disable in AD.
- AD Accounts tab: UID/OU/mail settings.
- Settings → LDAP: connection settings and "Sync all AD users".

→ One "IT" tab with sub-tabs: Operations (I1) · Users · AD settings · Sync.
Settings keeps the app-wide configuration only.

### I5 Medium — common AD tasks are missing
There is no way to reset a password, unlock an account, or see/edit a
user's groups outside a workflow. `unicodePwd` is only written by the
onboarding account step. IT will keep using RSAT for these, so the app is
only half the tool.
→ On the user edit dialog: "Reset password" (reuse the one-time password
dialog from U1), "Unlock" (if `lockoutTime` > 0), and a read-only group
list with add/remove. Ask first which of these IT actually does weekly.

### I6 Medium — bulk actions are below 50 rows
`user_management.py:227-229`: "Enable in AD / Disable in AD" are drawn under
the table. With the default 50 rows per page, you select users at the top
and scroll a full page to find the buttons.
→ Put them in the table's top bar, shown when rows are selected
("3 selected · Enable · Disable").

### I7 Medium — the Users tab needs `is_superuser`
`shell.py:95`. Every IT member must be a superuser to see the user list,
which also gives them every other power. There is a `manage_users`
permission; the tab ignores it.
→ Show the tab for `manage_users`. Keep superuser-only actions guarded inside.

### I8 Low — AD Accounts form shows raw field names
`uid_min`, `users_ous`, `eligible_groups`, `home_directory_template`, no help
text. An empty `users_ous` breaks the AD step but nothing flags it.
→ Labels + one-line help per field, and a warning banner when `users_ous` is
empty (feed it to I1 too).

## Everyone

### E1 High — 11 tabs don't fit
At 1366 px the header scrolls: "AD Accounts" is cut, "Users" is off-screen.
At 390 px no tab label is visible at all, only two arrows (screenshot:
phone dashboard). A student never needs Audit log or AD Accounts, but the
admin sees everything flat.
→ Keep in the bar what everyone uses: Dashboard · Services · People ·
Bookings · Floor plan. Put "New request" as a button on the dashboard
(it's an action, not a place). Group admin tabs under one "Admin" (or
"IT") menu. Below ~700 px use a drawer (hamburger) instead of tabs.

### E2 Medium — the language toggle doesn't show the current language
`shell.py:165-167`: `toggle-color=white` on white text. "EN FR" look the
same whichever is active. Also, a browser in French gets English on first
visit.
→ Underline or bold the active one. Default to the browser language when
nothing is stored.

### E3 Medium — no clear entry point for a student or scientist
A member with no role permissions lands on welcome cards, "Nothing pending",
"No requests yet". Nothing says what they can do here.
→ Show 3-4 quick actions on an empty dashboard ("Book a room", "Find a
person", "Request VPN access"), driven by permissions. The Services tab
already holds the links; reuse it.

### E4 Low — "My profile" goes to the directory list
The account menu's "My profile" switches to the People tab
(`shell.py:172`), not to the user's own card.
→ Open the user's own entry directly.
